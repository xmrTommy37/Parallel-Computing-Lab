\section{Discussion}
Run on a machine with 20 physical cores, the experiments paint a much cleaner picture of the algorithm's intrinsic behaviour than a resource-starved node would. The Forest Fire automaton is embarrassingly parallel within each time step, and the near-ideal scaling of the computation-only time (Figure~\ref{fig:commcompute}) confirms it: doubling the process count halves the useful work almost exactly. What ultimately bounds the observed speedup is no longer core oversubscription but two subtler, hardware-rooted phenomena: the shared memory bandwidth and the packing cost of the halo exchange.

Three findings deserve emphasis. First, the code now scales monotonically all the way to $p = 20$ (Table~\ref{tab:speedup}), reaching a $12$--$13\times$ speedup with an efficiency of $0.60$--$0.72$; the collapse we would expect on an 8-core node simply does not occur because every process owns a real core. Second, the communication finally exhibits the textbook topology trade-off: at $N = 4000$ the 2D block moves less data than the 1D slab and its communication time drops below it (Figure~\ref{fig:topology}, right). Yet, and this is the most instructive result, the 1D decomposition still wins on wall-clock time, because its computation is cheaper: row-contiguous slabs vectorise and cache better than the strided, explicitly-packed column halos of the 2D scheme. The ``best'' topology is therefore not an absolute property of the algorithm but the outcome of a competition between communication volume and memory-access locality, and on a shared-memory node locality wins. Third, the weak-scaling study exposes a memory-bandwidth wall: even with a constant per-process workload the computation time rises by 50\% from $p=1$ to $p=16$, because all cores contend for the same memory channels. For this bandwidth-bound stencil, that contention, not the halo exchange, is the true single-node scalability limit.

\subsection{Limitations}
The overriding caveat remains that all experiments ran on a single shared-memory node, so the ``communication'' we measured is memory-copy and synchronization cost, not network traffic. This is precisely why 2D blocking did not pay off: on a real interconnect, where per-message latency and bandwidth dominate, the $\mathcal{O}(N/\sqrt{p})$ volume of the 2D scheme would matter far more than the modest computation-side differences we observed. The single-process speedup offset ($E>1$ at low $p$) is an artifact of comparing against a sequential baseline that re-pads the array every step; we reported the baseline-independent figures alongside it, but a fully fair study would use an identically-optimised serial reference. We also fixed the two probabilities and the initial density, so nothing here characterises the model's self-organized-critical physics; our goal was performance, not phenomenology. Finally, wall-clock timings on a 20-core socket are sensitive to NUMA placement and OS scheduling; three repetitions damp but do not eliminate this noise, and we did not pin processes to cores.

\subsection{Possible improvements}
The clearest next step is to overlap communication with computation using non-blocking primitives (\texttt{MPI\_Isend}/\texttt{MPI\_Irecv}): a process can post its halo exchange, update its \emph{interior} cells, which do not depend on ghost data, while the messages are in flight, and update the border cells only once the transfers complete. Given that communication reaches $20\%$ of the runtime at $p=20$, this could recover a substantial fraction of the lost efficiency. Second, the column halos of the 2D scheme should be exchanged with MPI derived datatypes (\texttt{MPI\_Type\_vector}) instead of explicit \texttt{.copy()} buffers, which would remove the packing overhead that currently makes 2D lose to 1D. Third, since the single-node ceiling is memory bandwidth, a hybrid MPI\,+\,threads scheme (or simply fewer, wider processes) could reduce redundant memory traffic. Finally, a genuine assessment of the 1D-versus-2D trade-off, and of strong scaling beyond 20 processes, requires a multi-node cluster, where we predict the perimeter-minimizing 2D layout would at last become the faster option.
